Set Neo4j resource limits and a fixed Cypher parallel runtime worker count in the `small`, `medium`, `medium-data`, `large` and `large-data` config presets. Without a CPU limit, the JVM reports every logical processor on the node as available, and Neo4j sizes its Cypher parallel runtime from that count: `server.cypher.parallel.worker_limit` defaults to `0`, which starts one worker per available processor. On a large node Neo4j started far more parallel runtime workers than the preset's CPU request covered, oversubscribing the CPU the preset was sized for. The presets now set `server.cypher.parallel.worker_limit` to 4, 8 or 16, and the CPU request and limit one core above it (5, 9 or 17), leaving a core of headroom for the Neo4j threads that run alongside the workers. The memory limit equals the memory request, so the Neo4j pod runs in the Guaranteed QoS class; the JVM heap and page cache stay pinned by `server.memory.*`, leaving at least 7 GB of each limit for off-heap allocations and the operating system. Override `infrahub.neo4j.neo4j.resources` to change the requests and limits, or `infrahub.neo4j.config.server.cypher.parallel.worker_limit` to resize the worker pool.
