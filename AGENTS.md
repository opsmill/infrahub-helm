# Infrahub Helm charts

Helm charts that deploy Infrahub on Kubernetes. They are published to
`oci://registry.opsmill.io/opsmill/chart`. `stable` is the only main branch: open every pull
request against it.

## Charts

Each chart lives in `charts/<name>/`:

- `infrahub`: the community chart. It holds the templates of the Infrahub server, the task workers
  and the jobs, and installs Neo4j, Redis, RabbitMQ, NATS and the Prefect server from upstream
  charts.
- `infrahub-enterprise`: wraps the `infrahub` chart and sets its values under the `infrahub:` key.
  Its own templates only check the values and print the install notes. It holds the size presets
  (`values.small.yaml`, `values.medium*.yaml`, `values.large*.yaml`) and `values.openshift.yaml`.
- `infrahub-backup`, `infrahub-observability`, `infrahub-mcp`: optional charts that the `infrahub`
  chart installs when `<name>.enabled` is set.

The charts depend on each other through the registry, not through local paths: `infrahub` pins a
version of `infrahub-backup`, `infrahub-observability` and `infrahub-mcp`, and
`infrahub-enterprise` pins a version of `infrahub`. A change to a pinned chart reaches the chart
above it only after the pinned chart is released and the pin is updated.

## Changing a chart

- Describe each value you add in `values.yaml` with a `# --` comment.
- `README.md` is generated by [helm-docs](https://github.com/norwoodj/helm-docs) from
  `README.md.gotmpl`, `Chart.yaml` and the `values.yaml` comments. No CI job runs helm-docs, so
  update `README.md` in the same pull request: run `helm-docs --chart-search-root=charts/<name>`,
  or change the generated rows by hand. Edit `README.md.gotmpl` for any other text.
- Add a changelog fragment for each chart that changes:
  `uvx towncrier create --config charts/<name>/towncrier.toml +<short-name>.<type>.md`. The types
  are `security`, `removed`, `deprecated`, `added`, `changed`, `fixed` and `housekeeping`. A change
  to `infrahub` that reaches `infrahub-enterprise` through its `infrahub` dependency also gets a
  fragment in `infrahub-enterprise`. The root `changelog/` directory only holds the template that
  the charts share.
- A pull request does not have to bump the chart `version`: the change ships with the next release
  of the chart. When you do bump a chart that another chart pins, update the pin and bump that
  chart too.
- Commit messages follow Conventional Commits, with the chart as scope, for example
  `fix(infrahub-enterprise): ...`.

## Tests

- `make lint` runs `helm lint` on every chart.
- `uv run pytest -v -m <marker> tests/e2e` installs the local charts into a throwaway vcluster and
  tests them. The markers are `infrahub`, `enterprise`, `backup`, `observability` and `mcp`. See
  `tests/README.md` for the tools it needs and for the manual tests.
- The Grafana dashboards of `infrahub-observability` are not committed. Run
  `./scripts/sync-upstream.sh` before you test or package that chart.
- CI (`.github/workflows/ci.yml`) runs the lint and end-to-end jobs only for the charts that a pull
  request changes. A change to `charts/infrahub/` also runs the `infrahub-enterprise` and
  `infrahub-mcp` jobs, and a change to `tests/` runs all end-to-end jobs.
- No CI job deploys the size presets. To test one, install the local `infrahub-enterprise` chart
  with `-f charts/infrahub-enterprise/values.<preset>.yaml`, and point its `infrahub` dependency at
  the local `charts/infrahub` the way `tests/e2e/conftest.py` does.

## Releases

- A chart is published when a GitHub release named `<chart>-<version>` is published here. To cut
  one, bump `version` in `Chart.yaml`, merge, then run the "Publish Helm Chart" workflow
  (`.github/workflows/publish-helm-chart.yml`) for the chart. It builds `CHANGELOG.md` from the
  fragments, tags the commit and creates the release, which packages and pushes the chart.
- Each `values.<flavor>.yaml` file of a chart is also published as chart version
  `<version>-<flavor>`, with the file merged into `values.yaml`. Adding such a file adds a
  published chart.
- Every final Infrahub release publishes the `infrahub` chart from `stable`, and every final
  Infrahub Enterprise release publishes the `infrahub-enterprise` chart from `stable`. Before that,
  the Infrahub release process sets `appVersion`, the chart `version`, `prefectTag` and the
  `infrahub` dependency of `infrahub-enterprise` here. So a change to these two charts that is
  merged to `stable` ships with the next Infrahub release.
